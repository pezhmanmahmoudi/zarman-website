# Unified admin transactions workspace

The admin Transactions section now includes the former request queue. The sidebar has one Transactions entry. Existing request URLs redirect to `/admin/transactions`; request detail links redirect to `/admin/transactions/requests/[request-id]`.

- **Active:** online requests and manual transactions, ordered by handling deadline and creation time. Stage filters cover review, payment verification, settlement, waiting for the customer and outstanding refunds. A request and its accounting transaction are one row, joined through the existing unique `exchange_requests.transaction_id` relationship.
- **History & reports:** the same responsive transfer rows, with status, customer/reference search, direction and date filters, pagination, receipts and existing IFTI export controls. View opens a focused transaction drawer. Completed manual transfers and online requests offer **Edit amounts**, using the atomic correction workflow described below. Unsettled online requests use their existing request workflow.
- **Settings:** Rates, fees & rewards contains the existing platform configuration and promotions. Transfer service contains request availability, payment accounts, notifications, hours and terms. Both forms remain mounted when switching sections, preserving unsaved changes and the existing version-checked settings save.

Request approvals, receipt review, cleared-funds confirmation, reconciliation, messages and optional email delivery still use their existing server commands. Manual approval remains a separate workflow within the same workspace. The workspace consolidation itself introduced no database migration or data conversion; the subsequent reopening feature below has its own migration.

Rejected online requests now offer **Reopen request** in the request detail action panel when no funds have been recorded. An administrator enters an internal reason, reviews the existing amounts and confirms reopening. The request returns to review and its linked transaction becomes pending in one version-checked, idempotent command. Existing references, quotes, receipts, messages and rejection history remain intact. Continue with **Approve request** for an unapproved request, or **Confirm funds received** when payment was already approved. Reopening itself does not confirm receipt or settlement.

This reopening feature requires `supabase/migrations/20261012_57_reopen_rejected_requests.APPLY_MANUALLY.sql`, applied after migrations through 56 before deploying the application change. Installation does not modify existing requests. The RPC is service-role only and independently checks administrator access, the rejected state, and the absence of payments, refunds, fee accounting and payout execution. Previously approved payment windows are renewed using the saved policy and current priority-capacity checks; the original approval timestamp is retained. The reopening reason is internal; the customer sees a reopening milestone and receives an email only if the administrator selects it. A missing RPC produces an error with no fallback status update. Verification uses synthetic data in PGlite and isolated UI/server-action tests; no live transaction is changed by those tests.

The admin workspace refreshes through the explicit Refresh controls and retains its last successful data if refresh fails. There is no polling or refresh on focus/tab return. Admin request details, including email delivery status, also refresh manually, with no realtime subscription; initial loads and updates after submitted actions remain available. Admin error recovery waits for Try again or Dashboard. History selections are tied to the selected record's status and trade type so a refresh cannot turn report selection into deletion. Pending reads use bounded batches to avoid silently truncating the queue at the API row limit; outstanding refunds remain accessible even after rejection or cancellation.

Active and history share `TransactionTable`, built on `AdminDataTable`, `AdminRecordDrawer`, `AdminWorkspace.module.css` and the `AdminTable.module.css` foundation. Identity Verification, Customers, Ledger and Audit Log also use these shared primitives (see `admin-table-system.md`). Customer names are bold and primary; references are secondary. Customer pays and Recipient gets have separate, right-aligned columns. Status uses restrained semantic colors. Date filters open on demand; the date pickers sit in bounded fields, avoiding the previous full-width stacking problem. Invalid date ranges show an inline error.

At narrow container widths, each row becomes a labeled card. The detail drawer uses the existing accessible AdminDialog for focus trapping, Escape, scroll containment and focus restoration. It groups amounts, destination and record information; manual edits reuse the validated field editors. Transaction rows show one compact, consistently sized next-step control: **1 Review**, **2 Payment**, **3 Settlement**, with a matching workflow key beside search. The step follows the request's payment milestones rather than its queue filter: a funded hold stays at payment verification. Waiting actions are muted; refunds and historical records use icons rather than misleading step numbers. A separate ellipsis opens request details and the existing rejection shortcut. Pending manual records open their approval dialog from the detail drawer; approved manual records retain Reject there. Request shortcuts only navigate to the existing forms and never approve, send or reject automatically. Requests keep their staged workflow rather than invoking legacy transaction commands. Report selection remains in the header, with its action bar appearing only after selection. Dates remain in English and display Sydney time. Existing English and Persian customer workflows are unchanged.

The numbered action design changes presentation and navigation only. Desktop controls are 36px high, with 44px touch targets on coarse pointers. Keyboard focus indicators and reference-specific accessible labels are retained. No tests, build or automated validation were run for this design update, as requested.

Verification: admin workspace tests are included in `npm run test:admin`; request UI and notification tests remain in the existing request suite. A read-only Supabase HEAD request validates the existing relationship and search query without retrieving customer records or modifying data. Visual browser review is omitted at the user's request. Nothing is deployed by this change.

## Correcting completed transfer amounts

Apply `supabase/migrations/20261013_59_completed_transaction_amounts.APPLY_MANUALLY.sql` after request migrations through 58, then deploy the application. The migration creates the correction commands, history, receipt revisions and guards; it does not edit any existing transaction. The application does not fall back to separate writes when this migration is missing. This implementation has not applied the migration to the live database.

Open a completed transfer in **Transactions → History & reports → View → Edit amounts**. Enter the actual customer payment, actual recipient amount and an internal correction reason. The same editor is available in completed request details, customer transaction editing and linked trade ledger details. If several deposits funded the request, their corrected amounts must add up to the customer payment. Original deposit records remain available through the existing correction history.

The administrator-only database command locks and checks the current financial state, validates currency precision, and saves the request quote, transaction amounts, linked trade ledger, deposit corrections and a revised receipt in one transaction. It retains the settlement date, account mapping and recorded service fees, deriving the new exchange rates from the corrected amounts. Changes to accrued bank-fee estimates follow the corrected Toman amount; bank costs already posted as actual expenses remain as recorded. A stale editor must reload. Retrying an identical command cannot post the correction twice.

Customer screens, treasury and new exports read the updated transaction/request/ledger rows. Daily, customer and account report tables and monthly/yearly materialized views are rebuilt inside the correction transaction; refresh failure rolls back the entire correction. The Toman valuation of settled priority fees follows the corrected quote rate while their original currency amounts are retained. Both admin and customer route caches are invalidated, and online requests use the existing customer refresh signal. The receipt download serves the latest revision; the original receipt and all revisions are retained. Already downloaded exports, previously delivered emails and externally submitted reports remain historical documents and are not rewritten or resent. Reporting submission markers are preserved.

The audit log records the administrator, reason and full before/after financial state. The customer timeline shows that amounts were corrected without exposing the internal reason. Correction does not reopen the transfer or initiate another payment. Older editors cannot update the financial fields of approved transactions or their linked trade ledger independently. No tests were run for this change, as requested.
